# hybrid 融合 + reranker 对照（T12 / o 任务）

> 日期：2026-10-31；主工程 `E:\project\LexWeave`；金标 `data/gold/gold_60.jsonl`（60 条，未换）。
> 环境：全程 CPU（`EMBEDDING_DEVICE=cpu`、`GRAPH_BACKEND=networkx`）。开跑前 `nvidia-smi` 显示 RTX 4060 已被另一会话的 python 计算进程占用（2109/8188 MiB、39% util），本任务未使用 GPU。
> 图路输入：n 任务的 `TwoHopRetriever`，官方值 R@5 **0.6111**（CI [0.5222, 0.7000]，median 224.7 ms）；图画像 1799 节点 / 5826 边，未重建。
> 文本基线：`retrieval.json#results.text`，R@5 **0.7472**（median 411.4 ms，router 档位）。
> 现有官方 hybrid：R@5 **0.7556**（median 395.7 ms）。

## 1. 结论（先行）

**没有达到 0.78。** 四格中最好的「加权融合 + 精排」= **0.7583**（95% CI [0.6750, 0.8361]），距目标 **−2.17pp**。点估计没到，但 CI 上界越过 0.78，说明 60 条样本下不能排除「真实值 ≥0.78」，也不能据此宣称达到。

| 排名 | 格 | R@5 | 95% CI | 是否 ≥0.78 |
|---|---|---|---|---|
| 1 | 加权 + 精排 | **0.7583** | [0.6750, 0.8361] | 否（−2.17pp） |
| 2 | RRF + 精排 | 0.7528 | [0.6667, 0.8306] | 否（−2.72pp） |
| 3 | RRF + 不过精排 | 0.7222 | [0.6444, 0.7972] | 否 |
| 4 | 加权 + 不过精排 | 0.7056 | [0.6222, 0.7861] | 否 |

**「reranker 值不值这 200 ms」：不值，至少不是精度上的提升点。** 在 CPU 上精排单项中位耗时 **+10.4 s**（不是 200 ms；200 ms 只可能来自 GPU 环境，本任务未测）。即便按 200 ms 的假想成本算：精排带来的配对增益是 +3.06pp（RRF）/ +5.28pp（加权），两个 95% CI 都含 0；相对文本基线只有 +0.56 / +1.11pp，也都不显著。它真正的作用是「把不过精排时被打散的文本排序拉回来」——两个不过精排的格比文本基线低 2.50 / 4.17pp，而不是把 hybrid 推到 0.78。

**瓶颈不是「候选不够」，而是「排序选不对」。** 融合后 25 条候选池的 oracle 选优上限是 **0.9194（RRF）/ 0.9250（加权）**，60 条里有 52/53 条的金标条文全部落在池内；实测精排只拿到 0.7528 / 0.7583，**选优损失约 16.7pp**。实体链接仍是图路的主要损失（金标概念作种子的 oracle 图路 0.7139，比实测 0.6111 高 10.28pp），但即使把种子换成金标，图路（0.7139）仍低于文本（0.7472），所以它不是 hybrid 未达 0.78 的唯一原因。

## 2. 2×2 四格明细

固定档位 `medium`（`top_k=5`、`hops=2`、权重 text 0.55 / graph 0.45），避免 router 逐题漂移。文本路取 top30（不过精排），图路取 2-hop top10，融合后取 25 条候选；精排格用 `bge-reranker-v2-m3` 对 25 条一起重排。

| 格 | 融合 | 精排 | R@5 | 95% CI | all@5 | median | p90 | top-5 变化（题/位置） | top-5 平均 Jaccard |
|---|---|---|---|---|---|---|---|---|---|
| rrf_norerank | RRF | 否 | 0.7222 | [0.6444, 0.7972] | 0.4667 | 545.3 ms | 726.1 ms | — | — |
| rrf_rerank | RRF | 是 | 0.7528 | [0.6667, 0.8306] | 0.6000 | 10886.5 ms | 14135.0 ms | **59/60 题，239/300 位** | 0.4272 |
| weighted_norerank | 加权 | 否 | 0.7056 | [0.6222, 0.7861] | 0.4833 | 545.3 ms | 726.1 ms | — | — |
| weighted_rerank | 加权 | 是 | **0.7583** | [0.6750, 0.8361] | 0.6000 | 11042.8 ms | 13795.7 ms | **58/60 题，248/300 位** | 0.4385 |

- 「top-5 变化」按位置逐位比对：RRF 精排前后 59/60 题至少换过一条，300 个位置里换了 239 个（79.7%）；加权是 58/60 题、248/300 位（82.7%）。平均 Jaccard 只有 0.43–0.44。
- 结论很直接：**精排几乎把所有题的 top-5 都重排了一遍，却只换来 +3.06 / +5.28pp 的净增益**——大量是无效抖动，不是定向纠错。
- `all@5` 从 0.47/0.48 提到 0.60，说明精排确实让一部分题「全中」，但没转化成足够多的 R@5。

**没有任何一项的 95% CI 排除 0。** 60 条样本下，融合方式（RRF vs 加权）与是否精排都撑不起显著差异；点估计只能当方向参考。

口径提醒：文本基线来自官方 `text` 档（router 逐题选档，31 medium / 29 complex），本节四格固定 medium。R@5 只看 top5，但 complex 题的权重是 0.45/0.55，与固定 0.55/0.45 不同，所以「vs 文本基线」的配对差值不是完美因果对照，只用于给量级。

## 5. 延迟与精排成本

| 组件 | 中位耗时 |
|---|---|
| 文本路（dense+BM25+RRF，top30，不过精排） | 251.9 ms |
| 图路（2-hop，top10，含实体链接） | 278.4 ms |
| 融合（RRF / 加权） | 0.1 ms |
| **精排（25 条，bge-reranker-v2-m3，CPU）** | **10377.8 ms（RRF 格）/ 10404.7 ms（加权格）** |

- 不过精排整链路中位 **545.3 ms**；过精排 **10.89 s / 11.04 s**，p90 13.8–14.1 s。
- 说明：文本/图路组件每题各测一次、四格共用同一组测量；融合与精排按格单独计时；不含模型加载与图构建。
- 官方 `text` 档 median 411.4 ms（含精排 30 条），比本次 CPU 精排快约两个数量级——那个量级只可能来自 GPU。**本任务没有实测 GPU 精排延迟**，200 ms 是题面给的口径，不是本报告测出来的数。

**判断**：按 200 ms 算，精排是「用 200 ms 换 +3~5pp 且不显著」，精度上不划算；按 CPU 实测 10.4 s 算，更不划算。若延迟是硬约束，唯一保留精排的理由是「不过精排会让融合比文本基线掉 2.5–4.2pp」，即精排在这里是止损项，不是增益项。

## 6. 上限与瓶颈归因（全部为 oracle，不是可部署实测）

| oracle | R@5 | 定义 |
|---|---|---|
| 金标概念作 2-hop 种子（图路） | **0.7139** | 跳过 linker，直接把金标概念当种子，排序器不变 |
| 金标种子图路 + 文本 RRF（不过精排） | 0.7444 | 同上，再与文本路做同参数 RRF |
| 两路 top5 并集 oracle | 0.8333 | 文本 top5 ∪ 图 top5 里最优选 5 条 |
| 融合候选池 oracle（25 条） | **0.9194（RRF）/ 0.9250（加权）** | 融合后池内最优选 5 条；52/60、53/60 题金标全在池内；仅 1 题池内无金标 |

> n 任务报告给的图路金标种子上限是 ≈0.73；本次同口径复算为 0.7139，差 1.6pp 属于两次实现/运行差异（均为 oracle，只作参考，不作为可部署指标）。

**怎么读这三层：**

1. **候选层够用。** 融合池已经包含 92% 的金标覆盖率，0.78 在候选结构上可达；缺口在「从 25 条里选 5 条」。
2. **精排的选优损失约 16.7pp。** 池上限 0.9194/0.9250，实测 0.7528/0.7583。精排把 top-5 换了 80% 的位置，只补回 3–5pp，说明它对短法条的判别力有限，不是「候选里没有正确答案」。
3. **实体链接仍是图路的头号损失，但不是全局瓶颈。** `path_recall=0.5694`（150 个金标概念实例只链上 85 个，65 个漏掉）；换成金标种子后图路 0.6111→0.7139（+10.28pp），这 10pp 确实被 linker 吃掉了。但金标种子的图路（0.7139）仍低于文本（0.7472），金标种子 + 文本 RRF（0.7444）也没到 0.78——**即使实体链接全对，当前图结构与融合方式也不足以把 hybrid 推过 0.78**。
4. 因此本题的诚实结论是：**0.78 不是被 linker 单点卡住的；它是「图路本体上限偏低 + 精排选优能力不足」共同造成，后者占比更大。**

## 7. 参数

| 参数 | 值 | 说明 |
|---|---|---|
| 文本候选 | top30 | dense+BM25 RRF，不过精排；与生产 hybrid 对齐 |
| 图路候选 | 2-hop top10 | `TwoHopRetriever`，`keep_inferred=True` |
| 融合候选 | 25 条 | 与生产 `RERANK_CANDIDATES` 对齐 |
| 融合权重 | text 0.55 / graph 0.45 | `LEVELS["medium"]`，固定档位 |
| RRF k | 60 | 全局 `settings.rrf_k` |
| 加权融合 | 两路各自 min-max 归一化后加权求和，缺项 0 分 | 文本侧用文本路 RRF 分数，图侧用 2-hop 分数 |
| 精排模型 | `BAAI/bge-reranker-v2-m3`，max_length 512，batch 32 | CPU fp32 |
| 覆盖加成 | 0.0 | 本对照不叠加生产里的 `+0.02×coverage`，保持 2×2 干净 |
| 档位 | `medium` 固定 | 不启用 router，避免逐题切档 |
| bootstrap | 1000 次，seed 20261031，配对 | 结果落盘在 `retrieval.json#results.hybrid_rerank.bootstrap` |

**没有为了够到 0.78 再做权重网格。** 若在同一个 60 条上搜到 0.78 再写进报告，属于 in-sample 过拟合；本任务只按预注册的四格报数。

## 10. 口径与边界声明

- **in-sample，无留出集。** 四格都在同一批 60 条金标上测，参数是按 n 任务定好的、没有在本任务上二次搜索；但 60 条里 1 条题 ≈ 1.67pp（两概念题约 0.83pp），CI 很宽，所有差值都不显著。
- **cross_law 只有 10 条**，1 条题 = 10pp，该桶只报方向。
- **精排延迟是 CPU 实测**，不代表 GPU；「200 ms」是题面口径，本报告没有 GPU 数字。
- **文本基线不是同档位复算。** 官方 text 档走 router（medium/complex 混合），四格固定 medium；配对差值只作量级参考。
- **oracle 不是实测能力。** 金标种子、池内选优都用了评测时才知道的答案信息，只用来定位上限与瓶颈，不能写进可部署指标。
