# LexWeave 优化评估（算法岗求职视角）

> 评估日期：2026-11-10
> 评估对象：`E:\project\LexWeave`（KG-RAG 项目）及其在简历、技术档案、面试逐字稿中的表述
> 评估原则：只以仓库内可复算产物为准；不把包装当优化；不为凑指标补无依据的边

---

## 0. 结论摘要

1. **最优先的不是加功能，而是修口径。** 简历里 4 个数字/表述与仓库当前产物不一致，其中 2 个属于"一打开 JSON 就露"的硬伤。这类问题对算法岗是**一票否决级**风险，成本却只有半天。
2. **项目最大的方法论缺口是"没有留出集"。** B3/B6 全部 60 条 in-sample，README 自己标注了"无留出集"。而 `gold_200` 里天然有 140 条未参与调参的题（70/46/24），补一次留出评测是投入产出比最高的真实改进。
3. **图路弱是真实的，根因是实体链接，不是图建得差。** 150 个金标概念只链上 85 个，oracle 图路也只有 0.7139。想提升 hybrid，必须先把链接召回做上去；直接扩词典/加边属于凑数，已被项目自己证伪。
4. **CITES 边（97 条）建了但主链路没用**（`use_cites=False`），这是现成的、可解释的结构信号，值得做一次诚实的消融。
5. **B6 的默认档位与自己的消融结论相反**：API/UI 默认 C（多 Agent），但 C 的 grounded 比 A_gates 低 16.7pt、调用多 1 次。把默认改成 A_gates 是零风险的"用数据做产品决策"故事。
6. **vLLM 9.95×、ASR 20%→5% 不属于这个仓库**：产物在 `work/a2-inference-bench`、`work/parallel-run/T28`，本仓没有 vLLM 服务代码、没有训练代码。挂在 KG 项目下经不起"代码在哪"的追问。

### P1. 留出集：把 B3/B6 从 in-sample 变成 held-out（1–2 天）

**现状问题**
- README §5 标题就写着"60 条金标，in-sample，无留出集"；coverage 系数、RRF k、链接阈值都在同一批 60 条上校准过。
- 这是算法岗面试最容易被打的点："你的提升是不是在这 60 条上调出来的？"
- 目前 1 条题 = 1.67pt，二项标准误 0.064，任何 <2pt 的差异都无法下结论。

**具体改法**
- `data/gold/gold_200.jsonl` 已含 200 条，且 `gold_60` 是其子集；剩余 **140 条（two 70 / three 46 / cross 24）** 未参与 B3/B6 调参，天然可作留出集。
- 给 `scripts/eval_retrieval.py`、`scripts/eval_ablation.py` 加 `--gold` 参数（目前两处都硬编码 `data/gold/gold_60.jsonl`）。
- B3：在 140 条上跑 text / graph / hybrid，配对 bootstrap（按题重采样），报 R@5 + 95%CI。**无需 API**。
- B6：在 140 条里分层抽 60 条做 held-out 消融；四档 × 60 约 360 次生成调用（DeepSeek 单价下约 ¥1–3），需你确认是否愿意花这笔钱。
- 报告里同时保留 in-sample 与 held-out 两列，不要只报好看的那列。

**预期收益**
- 标准误从 0.064 降到约 0.042（n=140），结论更稳。
- hybrid−text 的 +0.84pt 很可能在留出集上仍然落在噪声内，甚至变负——**这是可以接受的结果**，它把"图路在本任务上不加分"从推测变成结论。
- 简历可写："在 140 条未参与调参的留出集上复算，hybrid 与纯文本差异为 X（CI …）"。

**风险 / 诚实边界**
- `gold_200` 的条文锁定用了 bge-reranker，而检索也用它，存在共享组件偏置；报告里要写明"留出的是题，不是组件"。
- 不要把 140 条再拿去调 coverage / k / 阈值，否则又变成 in-sample。

**面试讲法**
> "我原来所有检索数字都是 60 条 in-sample，这是硬伤。后来我把 200 条金标里没参与调参的 140 条拿出来做留出集，结论是 hybrid 的增益从 +0.84pt 变成 X。哪怕变负我也照报，因为 in-sample 的提升不能当能力。"

### P2. 指标拆分：`cite_precision` 的天花板与 `grounded` 的污染（0.5–1 天，无 API）

**现状问题**
- `cite_precision = 命中 ÷ 答案引用数`，金标平均只要 2.02 条，答案却引 3.4–6.1 条，理论上限只有 0.37–0.52。指标把"引得多"惩罚成"引错了"，无法区分两类错误。
- `grounded`（答案引用 ⊆ 检索结果）被 repair 强行剔除越界引用后天然偏高：A_gates 的 1.0000 里有 5/60 是修复的机械结果。
- README §12 局限 10/11 已经点名"本轮未做"，属于自己挖了坑没填。

**具体改法**
- `ablation.json` 的每个 row 已存 `citations`，`gold_60.jsonl` 有金标引用，**可完全离线重算，不花 API**。
- 新增三个量：
  1. `must_cite_recall`（现有 `cite_recall`，保留）；
  2. `precision@|must|`：把答案引用按出现顺序取前 |must| 条算精度，消除长度惩罚；
  3. `over_citation_rate = (|answer_cites| − |must|) / |must|`，单独报告"多引"程度。
- `grounded` 拆成 `out_of_scope_cites`（越界引用条数）与 `grounded_after_repair` / `grounded_before_repair`，明确 repair 贡献。
- 检索侧加 McNemar 检验（按题配对命中/不命中），比只看 bootstrap 均值差更适合 0/1 指标。

**预期收益**
- 引用精度从"被长度压到 0.42"变成可解释的两个数；C 档"引得更少所以更准"的假象会被拆开。
- 不改变模型，但让"我知道自己的指标哪里有问题"变成可展示的证据。

**面试讲法**
> "我的引用精度一直上不去，后来发现不是模型引错，是指标把'多引'算成了'引错'——金标平均只要 2 条，答案引 5 条，精度上限只有 0.37。我把它拆成 must-cite 召回、定长精度和超额引用数三个量，才看清 C 档那 3.4pt 里有一半只是引得更少。"

### P3. 默认档位与消融结论对齐（0.5 天）

**现状问题**
- `POST /ask` 与 UI 默认 `tier="C"`（多 Agent + 五闸），但 `ablation.json` 显示：
  - C 的 grounded 0.8333 < A_gates 1.0000（差 16.7pt，CI 不含 0）；
  - C 的 LLM 调用 2.22 次 vs A_gates 1.22 次；
  - C 的中位延迟 3279ms vs A_gates 2187ms；
  - C 的五闸全过 81.7% < A_gates 98.3%。
- A_gates 已实现，但 API 的 `pattern="^[ABCabc]$"` 不暴露它。

**具体改法**
- API 与 UI 默认改为 A_gates（或 A，如果希望更保守），C 保留为可选的"多 Agent 对照档"。
- 更新 README §8 的"架构默认值"段落；补一行"默认档由消融结果决定，不是由架构复杂度决定"。
- 重跑一次成本表确认 1.22 次调用与 2187ms 没变。

**预期收益**
- 真实成本下降约 1/3 调用、延迟降约 1.1s，质量指标不降反升。
- 这是"用数据推翻自己架构"的强故事，比"我做了多 Agent"更打动算法面试官。

**面试讲法**
> "我最初默认走多 Agent，因为看起来更'高级'。但四档消融显示多 Agent 的 grounded 比单链路+闸门低 16.7pt，调用还多一倍。所以我把默认改成了 A_gates，把多 Agent 降级成对照档。架构复杂度不是卖点，消融结果才是。"

### P5. CITES 条文级扩展（2–4 天，CPU，可能 0 收益）

**现状问题**
- `CITES` 97 条边已经建好，`graph_retrieval.retrieve(use_cites=...)` 也实现了，但**主链路和评测全部默认 `use_cites=False`**，这层结构信号完全没用。
- 图路走"概念→条文"，而实体链接漏了 65/150 个金标概念；条文级 CITES 扩展不依赖概念链接，是一条绕开瓶颈的路径。

**具体改法**
- 在 `HybridRetriever.retrieve` 里，对文本路 top-3 命中做 CITES 1 跳扩展，把目标条文加入候选池（不直接加分），再统一精排。
- 在 60 条 dev 上做 2×2 消融：`use_cites` × `use_rerank`，报 R@5、all@5、路径准确率。
- 最终数字在 P1 的 140 条留出集上复算，**不能只在 60 条上调参**。
- 可选进阶：把 CITES 入度/出度作为一个特征，和 rerank logit 做轻量 LTR 融合（5 折 CV on dev），不要在 test 上搜权重。

**预期收益**
- 理论上限有限：候选池 oracle 已有 0.9194（52–53/60 题金标全在池内），所以最多只能救剩下 7–8 题；现实预期 **0~3pt**，很可能是 0。
- 但即使为 0，"图信号放在条文层比概念层更稳，因为不依赖实体链接"是一个可讲的负结果。

**面试讲法**
> "我的图路一直弱，根因是实体链接漏概念。我试过绕开它：不按概念走，直接从文本召回的条文沿 CITES 走一跳。结果是 X。这个实验的价值是区分了'图没用'和'概念链接没用'——如果是后者，换条文级扩展就能救；如果是前者，就该把图降级成解释层。"

### P6. 实体链接召回专项（3–5 天 + 少量 API）

**现状问题**
- 150 个金标概念实例只链上 85 个（0.5694）；即使拿金标概念当种子，图路 oracle 也只有 0.7139，仍低于文本 0.7472。
- 失败原因是口语说法（"押金""裁员"）没有规范别名，词典精确匹配落空，向量兜底阈值 0.85 又偏严。

**具体改法**
- 先在 **dev 60 条**上导出所有未链接的金标概念及其查询片段，做一张"漏链类型表"（无别名 / 别名歧义 / 阈值过严 / 概念缺失）。
- 按类型分别处理：
  - 无别名：从**条文正文和 dev 题**里挖候选别名（**禁止**从 140 条测试题里挖，那是泄漏）；
  - 阈值过严：在 dev 上扫 0.75–0.90，报链接召回 vs 误链率，不要只看下游 R@5；
  - 概念缺失：只补"正文里真实出现且有定义/规制证据"的概念，补完跑 T01 清洗。
- 每加一批别名，都在 dev 上复算链接召回与图路 R@5，最后在 140 条留出集上验收。

**预期收益**
- 链接召回从 0.57 提到 0.70+ 是现实目标；图路 R@5 可能从 0.44 提到 0.50–0.55，但**大概率仍低于文本路**。
- hybrid 的增益取决于图路能否带来文本没召回的新条文；如果只是给已召回条文加分，R@5 不会动。

**诚实边界（必须写进报告）**
- 用测试题反推别名 = 泄漏；用条文正文挖别名是允许的，但要说明"别名来源=语料正文，不含金标题面"。
- 链接召回升不等于端到端升；两个指标分开报。

**面试讲法**
> "图路弱我一直归因于实体链接，但这是猜测。我先把 150 个金标概念的链接结果逐条导出，发现漏掉的 65 个里 49 个距种子只有一跳——不是图不够深，是入口没进来。然后我按漏链类型分别修，链接召回从 0.57 到 X，图路 R@5 从 0.44 到 Y。"

### P7. 211 条 `pending_semantic` 人工盲标（2–3 天人工，无 API）

**现状问题**
- DEFINES 710 目前只能给区间：机械误配 9.58% → 字面支撑 90.4%；严口径 559/710=78.7%；**211 条"字面命中但语义待判"没有结论**。
- 这是全项目最诚实、也最容易被追问的地方："你的定义边到底准不准？"

**具体改法**
- 用 `data/eval_out/defines_human_labels.csv` 的现有格式，新增 211 条待判行；**只给概念名 + 条文全文，不给别名、不给 cue**，避免判据被提示词带偏。
- 单人不重复盲标（不要假装双人）；如需 κ，找一位同学对其中 50 条独立标一遍，明确写"50 条子集、单次、非完整双盲"。
- 产出：真实语义精度 + 95% Wilson 区间；把标签、判据、脚本一起入库。
- 再用"精度过滤后的子图"重跑一次图路，回答"去掉低置信定义边，图路是升还是降"。

**预期收益**
- 把"未知"变成"有区间的数"。如果精度只有 70%，那正好解释图路为什么弱；如果 85%+，DEFINES 才真正配得上"强语义"。
- 这是简历里唯一能证明"我愿意做脏活、不拿代理指标糊弄"的证据。

**面试讲法**
> "我的定义边一直只敢报字面支撑率，不敢报精度，因为有 211 条字面命中但语义待判。后来我自己盲标完了：精度是 X%。标完我把低置信边过滤掉重跑图路，结果 Y。这件事让我确定：代理指标可以用来筛，但不能用来交付。"

### P8. 8GB 内存内的轻量部署 + demo（2–3 天 + 托管）

**现状问题**
- 单进程常驻约 3.4GB、检索峰值约 5.1GB；2C2G 云服务器跑不动，最低 8GB。简历没有可点开的 demo。
- 冷启动 30s（`api_bench.json` cold_start_ms 30335.6），首 token 26.7s，对演示不友好。

**具体改法**
- 预计算：把 bge-m3 向量、FAISS 索引、BM25 统计量全部落盘，启动时不加载编码器。
- 轻量模式：默认 BM25-only 或 dense-only（不加载 reranker），把 reranker 作为可选开关；`/health` 报当前模式与 RSS。
- 实测三档内存（bm25-only / dense / dense+rerank），写进 README；选出能在 4GB 跑的一档。
- 部署一个公开 demo（HuggingFace Spaces / 轻量云），简历放链接。

**预期收益**
- 简历多一个"可点开"的链接，校招筛简历时价值很高。
- 但这不是算法指标提升；不要把它写成"性能优化 8.9×"之类的旧故事。

**面试讲法**
> "我把检索拆成三档内存模式实测：BM25-only 是 X MB，加 dense 是 Y，加 reranker 是 Z。最后线上只开能跑在 4GB 的那档，reranker 做成按需开关。代价是 R@5 掉 N 个点，这个取舍我写在 README 里。"

### P9. 领域自适应 reranker / LTR（1–2 周 + GPU，高风险）

**现状问题**
- 候选池 oracle 0.9194，实际只拿到 0.7583——**瓶颈在精排选优，不在召回**。
- 当前用的是通用 bge-reranker-v2-m3，没有法律域适配。

**具体改法（如果做）**
- 只用 dev 60 条 + 条文正文构造训练对：正例=金标条文，负例=同法域 hard negative（BM25 高分但非金标）。
- 方案 A：cross-encoder LoRA 微调；方案 B：LambdaMART 融合特征（rerank logit、dense、BM25、图覆盖、CITES 入度、法域匹配）。
- 5 折 CV on dev 选参，**140 条留出集只跑一次**。
- 报告必须同时给 oracle 上限与 reranker 单独收益，避免把召回收益算进精排。

**预期收益**
- 如果成，R@5 可能 +3~8pt；如果败，也是一条"通用 reranker 在短法条上已经接近上限"的负结果。
- 校招周期内风险偏高；建议放在 P0–P7 之后，有时间再做。

**面试讲法**
> "我先算了候选池 oracle：0.9194，说明召回不是瓶颈，精排才是。所以我没继续加召回，而是拿 dev 集微调了一个法律域 cross-encoder，留出集上是 X。这个顺序很重要——先定位瓶颈，再决定训不训模型。"

## 3. 真实提升 vs 包装 vs 应排除

### 3.1 能提升真实指标（可复算）

| 事项 | 可能影响的指标 | 说明 |
|---|---|---|
| P1 留出集 | 所有 B3/B6 指标的口径 | 不保证数字变好，但让数字可信；标准误从 0.064→0.042 |
| P2 指标拆分 | cite_precision、grounded | 消除长度惩罚与 repair 污染，指标本身更接近真实能力 |
| P5 CITES 扩展 | 图路/hybrid R@5、all@5 | 预期 0~3pt；上限受 oracle 0.9194 限制 |
| P6 实体链接 | 链接召回、图路 R@5 | 链接召回 0.57→0.70+ 是现实目标；端到端增益不确定 |
| P9 reranker/LTR | R@5 | 潜在 +3~8pt，风险高 |

### 3.2 只是包装（不要算作优化）

- README 美化、加架构图、加 GIF、改标题：提升点击率，不提升指标。
- 把"DEFINES 候选边"改叫"强语义定义层"：只改措辞，不改事实，**且属于反向操作**。
- 把 60 条 in-sample 结果换个说法叫"内部评测集"：不解决留出集问题。
- 把 A6/vLLM/ASR 的数字重新排版进 KG 项目：归属错误，不是包装问题，是事实问题。

### 3.3 明确排除（会引入不可信数据）

| 方案 | 为什么排除 |
|---|---|
| 继续扩概念词典把 DEFINES 凑回 800 | 项目已实测：扩词典会带来规则路由精确率下降、hybrid 相对提升收窄、B6 波动；且新增边大量是角色词的"正面规制"，不是定义。为达标补无依据的边，违反你的诚实约束 |
| 用 LLM 盲判 211 条并当"精度"报 | 同一批边换提示词判定从 27% 漂到 63%，尺子本身在动；只能作预填，不能作金标 |
| 从 140 条测试题里挖别名/规则再报提升 | 直接泄漏；任何"测试集上 +Xpt"都无效 |
| 用 60 条反复调 coverage / RRF k / 阈值再报 | 过拟合；项目自己已把 0.478 的网格最优判为"不作为交付口径" |
| 声称 2C2G 可部署 | 实测 3.4GB 常驻 / 5.1GB 峰值，硬性不满足；只能做轻量降级模式并如实报降级代价 |
| 把 ASR/vLLM 继续挂在 KG 项目下 | 产物不在本仓，且 ASR 隐去"越权 25%→25% 未降"，属于选择性披露 |

## 5. 需要你决策的分叉

1. **B6 是否花钱在 140 条留出集上重跑？** 四档 × 60 条约 360 次生成调用，DeepSeek 下约 ¥1–3；不重跑就只能报 B3 留出集，B6 继续标 in-sample。
2. **是否愿意花 2–3 天做 211 条人工盲标？** 这是唯一能把 DEFINES 从"区间"变成"精度"的办法，但不能由模型代劳。
3. **vLLM / ASR 是移出 KG 项目，还是单独开一个"推理与安全"项目条目？** 两者都需要你确认对应仓库是否可公开。
4. **是否接受"hybrid 在留出集上可能变负"？** 如果目标只是简历好看，这一步可以不做；如果要经得起算法岗追问，这一步不能省。
